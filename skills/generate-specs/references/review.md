# The internal review loop

Two reviews, two review ids, so the draft's rounds do not use up the output's:
- **Part 1, the draft** (SKILL step 4): review id `<id>-draft`, target `<project-dir>/work/spec-draft/<id>/` (`sdkit review begin <id>-draft --target <path>`, `record <id>-draft ...`). Everything below applies to it.
- **Part 2, the output** (SKILL step 8): review id `<id>`, target `specs/<id>/` (the OpenSpec change). This is the evidence `sdkit spec publish` checks. Fresh reviewers get the reviewed draft and the change and answer one question set: is anything lost, invented, renumbered or contradicted (AC ids, decisions, non-goals), does `tasks.md` cover every AC, does `design.md` keep each decision's rationale, is the prose in `ANALYST_LANGUAGE`. `business-requirements.md` is read with the same question plus one more: does every statement trace to a spec file (the spec wins on a conflict), is every active AC accounted for, can a customer or a PM read the first paragraph and the rest without an engineer beside them (`sdkit review plan business-requirements`). Use the `feature-spec` rubric for `specs/**/spec.md`, `prd` for `proposal.md`, `adr` for `design.md` (`sdkit review plan <artifact>`). A change here that is more than a typo goes back to the draft loop and the propose step is redone.


1. `sdkit review plan <artifact>` for `prd`, `adr`, `feature-spec`: reviewers, standards, context.
2. Read and follow `egm-review-loop/SKILL.md` (EGM plugin `egm@egm`; find it in the host's installed plugin or skills directory) in this thread, once per artifact, with `TargetFile`, `SemanticTarget`, `Reviewers`, `Standards`, `GoldfishContext` taken from the plan. Its `disable-model-invocation` flag blocks a user-style invocation, not reading and following it; whether a host lets one skill do that is unverified. If it cannot be followed, use the `spec-reviewer` role via `sdkit run-role` (fresh process); if neither is possible, record NOT_RUN.
2b. Run `sdkit review lint <id>` before every round (it is mechanical: AC ids, gate markers, references, `tasks.md` coverage and its role structure). Fix every error yourself; reviewers are not spent on them. With `REVIEW_REQUIRE_LINT=1` `begin` enforces it.
2c. Cost control, all deterministic: `sdkit review plan <artifact> --round N` gives round N's reviewers (a rubric may set `REVIEWERS_R1`/`TIER_R1` for a cheap first pass; record that round with `--set cheap`, its PASS never publishes, a full-set round must follow). `sdkit review changed <id>` lists the files that differ from the last evidence: send reviewers only those, the others keep their earlier result. `sdkit review settled <id> --prompt` prints the topics a person already settled; paste it into every reviewer prompt (a finding that reopens one is rejected). `record ... --roles N` counts the reviewer runs; `sdkit review status <id>` shows rounds, trend, roles and says CONVERGED when more rounds only sample.
2d. **The intended shape is three rounds.** Questions first (SKILL step 2) and `lint` clean, then: round 1 reviews the whole draft (cheap set if the rubric defines `REVIEWERS_R1`), round 2 the full set on what changed, round 3 only a verification of the fixes. Defaults are on: `begin` uses no round on unchanged content, refuses while lint has errors and warns on AC growth. If round 3 still has MAJOR findings, do not open a fourth round: `sdkit review status` will say CONVERGED or the same findings keep sampling; take them to the analyst on one screen.
3. Before the first review of a document: `sdkit review begin <id>`. After the reviewers answer, write their findings to a file as `- <id> | <BLOCKER|MAJOR|MINOR> | <where> | <text>` and run `sdkit review record <id> --verdict PASS|BLOCK|PARTIAL|NOT_RUN --isolation fresh|none --findings <file>`.
4. Reviewers and generator are different fresh subagents. If the host has no fresh-subagent facility: `record --verdict NOT_RUN --isolation none`, tell the user, stop. `isolation=none` can never be PASS.
5. Each correction changes the content hash, which makes earlier evidence stale: run `begin` again, review only the changed artifacts, `record` again. After each round follow `triage.md`: fixable findings are fixed, decisions are asked of the user in batches, then the next round opens. Past the round cap `begin` exits 3: follow "At the round cap" in `triage.md` (findings one by one, then `begin <id> --final` for the single verification round).
6. `sdkit review check <id>` is the only test of "reviewed". `sdkit spec publish` runs it itself.
