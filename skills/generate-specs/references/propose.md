# Producing the OpenSpec change

The published output of `generate-specs` is an OpenSpec change, not loose markdown. The reviewed draft (`<project-dir>/work/spec-draft/<id>/`) is the input; `openspec-propose` writes the files.

1. Invoke the `openspec-propose` skill (host-specific invocation: `spec-driven-dev/references/hosts.md`) with change name `<id>` and the reviewed draft as the whole description. Tell it the prose language (`ANALYST_LANGUAGE`, default `tr`) and that OpenSpec keywords stay English. It creates `openspec/changes/<id>/`.
2. Move the result to the spec directory: create `specs/<id>/` if it is missing and move (with your file tools) the content of `openspec/changes/<id>/` into it (`proposal.md`, `design.md`, `tasks.md`, `specs/`, `.openspec.yaml` if present), then remove the empty `openspec/changes/<id>/`. `specs/<id>/` must hold exactly the change; no `prd.md` / `adr/` / `features/` loose files remain (`roles.json` is an added file, and so is `business-requirements.md`, written by the next step) (a leftover draft file is a bug, not output). `SPECS_DIR` overrides `specs`.
2b. Copy the draft's `roles.json` to `specs/<id>/roles.json` (it is part of the published spec; `sdkit tasks` reads it at the approved SHA).
3. Mapping, so nothing is lost:
   - PRD (problem, goals, non-goals, success criteria) -> `proposal.md` (Why, What Changes, Impact).
   - ADRs and design decisions with alternatives -> `design.md` (Context, Goals/Non-Goals, Decisions, Risks, Open Questions). Keep each decision's rationale. The draft's `## Roles` section (who does what, AC to roles, contracts between roles) goes into `design.md` as `## Roles`, unchanged.
   - Feature specs -> `specs/<capability>/spec.md`: one `### Requirement:` per behaviour, `#### Scenario:` per acceptance criterion, the `AC-<feature>-<n>` id kept in the scenario title. Ids are never renumbered; a withdrawn criterion stays, marked `withdrawn`.
   - `tasks.md`: the implementation breakdown for the developer, not the Jira tasks. One `## <n>. <Feature>` per behaviour family, and inside it one `### <Role>` per role from `roles.json` that has work in that feature (a role with none gets no heading, never a padded one). Each task is `- [ ] <n.m> <what, in that role's terms> (AC-<feature>-<n>[, ...])` and may end with `| after: <task id>[, ...]` when it needs another task first, within or across roles. Every task names at least one AC and together they cover every AC. Each role's tasks are its own work, not a copy of another's: for the login example, `### UI` designs the form, `### Frontend` builds it, `### Backend` validates the submitted credentials in the login service; the dependencies run UI before Frontend, and Frontend after the Backend contract it calls. The role headings use the role's name as in `roles.json` (`### UI`, `### Frontend`, `### Backend`, `### Solution Architect`).
   - Tell `openspec-propose` this shape and the picked roles (from `roles.json`) in its description; it writes the file, you do not rewrite it by hand. After the move run `sdkit review lint <id> --target specs/<id>`: a role heading the analyst did not pick, a task under no role, a task without an AC, an `after:` that names no task and an `after:` cycle are errors. Fix them (re-run `openspec-propose` for the file or correct it) before the fidelity review; a `tasks.md` that does not pass is not published.
4. Check with `openspec validate <id>` when the CLI offers it, and fix what it reports. Do not edit the OpenSpec skill's output beyond the move, validation fixes and the AC-id carry-over; content changes go back to the draft loop.
5. The draft directory is kept under `work/` (git-ignored) until the PR is open; it is never published.
