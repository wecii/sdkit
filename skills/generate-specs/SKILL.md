Drives the analyst from a pre-spec to a reviewed spec PR whose content is an OpenSpec change (proposal, design, tasks, specs). Mechanics (hash, branch, PR, version, metadata) are `sdkit spec`; the review evidence is `sdkit review`. Never write `spec.meta.json` or the review state by hand. `<kit>`, how to ask the user and how to start a fresh subagent: `spec-driven-dev/references/hosts.md`. Read a reference only at the step that names it.

**Two rules that never bend.** (1) PASS from the review is not approval: the Tech Lead approves by merging the PR; you never approve, merge or push to `main`. (2) The pre-spec directory (`PRESPEC_DIR`) is input only; nothing from it is committed or pasted verbatim into a published file without the analyst having seen it.

**One base per spec.** `generate-specs` writes the FIRST base `specs/<id>/` only. When `specs/<id>` already exists and is approved, a feature or fix on it is not a new id: stop and hand over to `update-specs`, which writes it as a change (`specs/<id>/changes/<slug>/`).

## Language

Everything written for people (questions to the analyst, the documents, the PR body, the final report) is in `ANALYST_LANGUAGE` (`sdkit.env`, default `tr` = Turkish; `sdkit.local.env` wins). Machine-read parts stay English: step banners, AC ids, review verdicts and severities, file names, OpenSpec section keywords (`## Why`, `## What Changes`, `### Requirement:`, `#### Scenario:`, `WHEN`/`THEN`). Pass the language to the generator and to the reviewers.

## Steps

Print `[sdkit] generate-specs - Step <n>/9: <name> - started|done` per step. At any point `sdkit spec next <id>` names the next step and says whether a person must act; between real decisions keep going without stopping to report (run to PASS), and stop only when it says `person`.

1. **Validate the input.** `sdkit prespec check <name>` must pass (exists, not empty, git-ignored, untracked). Pick the spec `<id>` (plain name, default the pre-spec name). If `specs/<id>/` already has a published version, stop and use `update-specs`. The `openspec` CLI and `openspec/` must exist (`sdkit doctor`); if not, stop and say so.
2. **Gaps, once, up front.** Before any draft, run the `prespec-gaps` role (light tier, fresh subagent; `sdkit run-role` where the host has none) on the pre-spec and `<project-dir>/project.md`, save its answer and run `sdkit prespec gaps <file>`: every open point comes back classed as *decision* (only a person decides), *fact* (only a person knows) or *default* (a safe default exists), as one list. Add what you see that it missed; do not drop its points silently. Ask decisions and facts in rounds you form yourself (host question tool, at most 4 per round, never padded to 4: group related points, put a point that depends on another answer in a later round, a default first); offer "accept all defaults" for the third class in one question. Each answer goes to `sdkit review settle <id>-draft ...` at once, defaults included, so nothing is asked or raised again. Do not invent requirements.
   **Roles, in the first round.** Ask which roles will implement the tasks of this spec (host question tool, multi-select over the kit's fixed list of eight). A question tool shows at most four options per question, so ask **two multi-select questions in the same round** (they use two of its slots), together covering all eight with a few words on each option: question 1 of 2: `solution-architect` (architecture decisions), `backend` (services, data), `frontend` (web UI code), `devops` (pipeline, infrastructure); question 2 of 2: `qa` (tests), `mobil` (mobile app), `ui` (screen design), `ux` (flows, usability). Say in each that choosing none of its options is allowed and that the other question has the remaining roles. The answers are merged; if neither question picked any role, ask once more, since a spec needs at least one. Write the answer to `<project-dir>/work/spec-draft/<id>/roles.json` as `{"roles":["backend","frontend",...]}`. Only these roles appear in the draft's "Roles" section and, later, in the tasks; a role added afterwards is a new question.
3. **Draft** (`references/generate.md`): PRD, ADR only where a real decision is made, feature specs with acceptance criteria that carry stable ids (`AC-<feature>-<n>`, never renumbered). Each criterion is testable: given/when/then with an observable result. Generation runs in its own subagent with only the pre-spec and the templates as input. The draft lives in `<project-dir>/work/spec-draft/<id>/`, never in `specs/<id>/`.
4. **Review the draft** (`references/review.md`, part 1): `sdkit review lint <id>-draft` first and fix its errors yourself; then follow EGM `egm-review-loop` in this thread, per artifact, under the review id `<id>-draft` (`sdkit review begin <id>-draft --target <draft dir>`, `plan`, `record`). Reviewers run in FRESH subagents, never the generator. A host that cannot start a fresh subagent records `NOT_RUN` and stops; it never records PASS.
5. **Analyse, ask, correct** (`references/triage.md`). You are the orchestrator: do not hand raw findings to the human. Triage every finding into one of three classes and act on each:
   - **Fixable from what you have** (pre-spec, `project.md`, code, a clear review standard): fix it in the draft.
   - **Needs a decision or a fact only a person has** (a term's meaning, a security or scope choice, a missing owner/date/number): collect it. Ask the user in batches with the host question tool (at most 4 per round, the safest default first and marked), each question saying which finding it closes. Never guess it and never leave it as an open question just to turn the review green.
   - **Reject** with a written reason (the finding is wrong or out of scope).
   Then write the answers into the draft as decisions (a decision/ADR entry or the requirement itself, with the rejected alternatives), fix the rest, and open the next review round for the artifacts that changed. Asking questions does not use up a review round; only `sdkit review begin` does. Repeat triage, ask, correct until PASS or the round cap (`sdkit review begin` refuses past `SPEC_REVIEW_MAX_ROUNDS`). Only then, for BLOCKER/MAJOR findings still open, walk them one by one as `references/triage.md` ("At the round cap") says: proposed edit, apply / answer / accept / reject; `sdkit review accept` runs only after the user's explicit yes for that finding (it records `JIRA_USER`), and `begin <id> --final` opens the one verification round outside the cap. Raising the cap stays the user's.
6. **Propose (the output).** Only after the draft review is PASS: invoke `openspec-propose` with the reviewed draft as its only input, so the result is an OpenSpec change, not loose markdown: `proposal.md`, `design.md` (with its `## Roles` section), `tasks.md` and `specs/<capability>/spec.md`, plus the picked `roles.json`. Place it at `specs/<id>/` (`references/propose.md`). The `AC-` ids, ADR decisions and traceability must survive unchanged. `tasks.md` is the implementation breakdown and must cover every AC; it is grouped by feature and, inside each, by the roles the analyst picked, each task in its own role's context (`references/propose.md`; `sdkit review lint <id>` enforces it). It is not the Jira task list (`generate-tasks` makes that later, starting from this structure).
7. **Business requirements.** Right after the proposal and before the output is reviewed: run the `requirements-writer` role in a fresh subagent (`sdkit run-role requirements-writer` where the host has none), mode create, to write `specs/<id>/business-requirements.md` (`references/business-requirements.md`): one readable document for developers, analysts, customers and PMs, the detailed form of `proposal.md` and `design.md` with the ACs and the role split on top. It is a derived view of the spec, never a source: it adds nothing the spec does not say, a gap the writer notices is a question for the analyst, not text in the file. Then `sdkit review lint <id> --target specs/<id>` must be clean (the derived-view marker, every active AC accounted for). It is in `specs/<id>/`, so the next step's review and the spec's hash cover it, and it travels in the same PR.
8. **Review the output and publish.** Run a fidelity round on `specs/<id>/` under the review id `<id>` (`references/review.md`, part 2): nothing lost, invented or renumbered against the reviewed draft, tasks cover every AC, `business-requirements.md` says nothing the spec does not. Then `sdkit spec init-meta <id>` and `sdkit spec publish <id> --title "<title>" --body-file <file>` (version 0.1, branch `spec/<id>`, one PR to `main`, reused on a re-run). It refuses without a fresh PASS bound to the current content, and (first publish) without `business-requirements.md`. Never force-push.
9. **Present the outcome**: PR URL, version, review verdicts and rounds (draft and output), accepted exceptions, open questions. State plainly that review PASS is not approval and the Tech Lead decides.
   **Then, one question** (host question tool, default no): does this feature need a user interface? Suggest yes when the picked roles include `ui`, `ux`, `frontend` or `mobil`; the analyst decides. On yes, invoke `generate-design <id>`: it reads the published spec, writes nothing under `specs/<id>/` and so changes neither its hash nor its review, and joins the spec's open pull request (one PR for spec and design). On no, you are done.

If `sdkit spec publish` fails, the version is untouched; fix the cause and run it again.
