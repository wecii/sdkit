Analyst environment (`SDKIT_ENV=analyst`). You derive the work; `sdkit tasks` does every deterministic check and `sdkit jira` is the task contract. Contract: `docs/design-role-aware.md` ("Task contract"). Read a reference only at the step that names it.

Input: Jira **parent key** (must exist), **spec id**, exact **SHA**. Never create a parent, never assign anyone, never read specs from the working tree.

## Steps

1. **Approval.** Write `tasks.json` skeleton (specId, specVersion, specSha, parent) and run `sdkit tasks acs <tasks.json>`. Every sdkit tasks verb except `cycles` first calls `sdkit spec approved-sha <id> --sha <SHA>` and refuses (exit 3) unless the SHA is on `origin/main` and the spec is approved. Stop on refusal; do not work around it.
2. **Read the spec at the SHA** only through `sdkit tasks acs` / `git show <SHA>:specs/<id>/...`. Not the working tree, not a branch. `acs` and `trace` skip ACs the spec marks `(withdrawn)` (they are not tested, so they need no task); `--include-withdrawn` lists them again.
3. **Revision with changes.** If `sdkit tasks changes <tasks.json>` lists slugs, this SHA is a merged revision: create tasks ONLY for the ACs `sdkit tasks acs <tasks.json> --revision` prints (what those changes added or modified), taken from each change's section of `tasks.md` (`## Change: <slug>`) and re-derived atomically; set `change` to the slug on every such task. Tasks of earlier changes already exist in Jira (done or not): never touch them; a modified AC always gets a NEW task that names the earlier task(s) of the same ACs in its `summary`. Ordinals like `3.12` are never identities. Use that AC list for step 4's `trace`. With no changes (first base), all ACs.
3a. **Start from the spec's own split.** If `sdkit tasks outline <tasks.json> [--revision]` succeeds (the `tasks.md` at the SHA has role headings: `generate-specs` wrote it that way), its output is the draft of 3b and 3c: one group task per feature, one role subtask per `### <Role>` with its ACs, its `tasks.md` lines as `steps`, `after:` as `dependsOn`, `qa` last. Take it as the starting point, not the answer: fill each group's `summary` (one sentence, below) and `risk` (rubric; never invent), check the roles against `design.md`'s `## Roles`, and regroup where `plan-check` says. It refuses with "no role headings" for a spec made before roles: then derive 3b and 3c by hand.
**What a person reads in Jira** (`references/task-format.md`, "The Jira text"): a title that says what to do, in the analyst's language, as an action ("Giriş formunu kodla", not "Frontend: Login"), and a short description. Do not write the description yourself: `steps` names the `tasks.md` lines and `sdkit tasks render` quotes them from the spec at the pinned SHA, so nothing is retyped and nothing can drift. `summary` is at most one sentence on why (a group's goal); leave it out when the steps already say it, and never add a requirement the spec does not state. By default the description is just "To do". Add `include` (`acs`, `after`, `source`) to a task only where it is unclear without it: `acs` when what makes it done is not obvious from the steps (a limit, a rule), `after` when the order matters and the Jira links do not show it, `source` when it must be traceable at a glance. Most tasks need none.
3b. **Derive atomic tasks**: one reviewable change each, with `ref`, `title`, `risk` (from `<project-dir>/project.md` rubric; never invent), `acceptanceCriteria[]`, `dependsOn[]` (refs). No scope: the developer finds the files in the repo at `spec-driven-dev`; never ask the analyst for paths. Format and key rules: `references/task-format.md`.
3c. **Split by role** (when `sdkit tasks roles <tasks.json>` lists roles; none = a spec made before roles, skip this step). Each task from 3b is a **group task** (the behaviour, its ACs, its risk). Under it, one **role subtask** per picked role that has work in it, read from the `## Roles` section of `design.md` at the SHA: `of` = the group's ref, `area` = the role, the ACs of that role's part (a subset of the group's), `summary` = what that role does, and for a consumer the contract it uses from the provider. Only picked roles; none for a role with no work in the group. When `designs/<id>/process.md` exists on the base branch (`generate-design`), a `ux` or `ui` subtask's `summary` points at it and names the `userTask` screens it covers; the flow is the designer's starting point, not work to redo. `dependsOn` is the order of the roles (design/ux before ui, ui and backend before frontend and mobil, devops where it must come first) and **`qa` is last in every group and depends on all its other subtasks**. `solution-architect` gets a subtask only when the group needs a real architecture decision. Group tasks carry no `area`; their `dependsOn` is plan-level, the real order lives on the subtasks. Subtasks do not repeat the group's summary. Format: `references/task-format.md`.
4. **Check**: `sdkit tasks plan-check <tasks.json>` first (size 12-20 group tasks, 4-12 ACs per task, single-AC and chain limits, gated ACs apart, risk rubric filled; the role subtasks are not counted in those rules but are checked for a valid role of the spec, ACs inside the group, a qa subtask after the others, and a role with no work; it prints `pack:` suggestions; apply them with `sdkit tasks regroup <tasks.json> --merge A,B,C --out <file>`), then `sdkit tasks trace <tasks.json> <ac-list>` (the `--revision` list for a revision) (every AC mapped, no orphan) and `sdkit tasks cycles <tasks.json>`. Fix and repeat; never confirm a plan that fails either.
5. **Plan gate**: show the analyst the `plan-check` summary and the AC-to-task table (group tasks with their role subtasks), dependencies and risk; wait for explicit confirmation. No Jira write before it.
6. **Validate and upsert** in `sdkit tasks order` sequence: `sdkit tasks render <tasks.json> <ref> --keys map.json --json` (it runs `sdkit jira validate-task`; any failure stops everything before the first write), then `sdkit jira upsert <externalId> <json>` (a group task is created as `JIRA_TASK_TYPE` under the parent; its subtasks as `JIRA_SUBTASK_TYPE` under the group, so `order` puts the group first and `map.json` must hold its key before its subtasks are rendered) (or the Jira MCP tools, `references/jira-write.md`). Append each result line to `results.jsonl` and add `externalId -> key` to `map.json`.
7. **Report**: `sdkit tasks report <tasks.json> results.jsonl --out <report.md>`. It exits 1 and says NOT a success if any task has no result. A failed external call is never reported as done; say which tasks exist and which do not, and rerun (idempotent by `externalId`, no duplicates).
